# Security and deployment

## Supported deployment

v0.1 is a local-first alpha for a founder or small team on a trusted machine. Run one application process with its SQLite database on a local disk. The default bind address is `127.0.0.1`; the server rejects unexpected Host headers. Do not put the database on a network filesystem or scale multiple containers against the same SQLite file.

### Desktop app

`foundry-desktop` (install the `desktop` extra) shows the same interface in a native window, served by the same application in the same process. Installers, code signing and updates are not built yet.

- **Data location.** The database, `owner.key`, the app's log (`desktop.log`) and the window's site-data folder live in the per-user application data folder: `~/Library/Application Support/Business Foundry` on macOS, `%LOCALAPPDATA%\Business Foundry` on Windows (not the roaming profile). On macOS and Linux that folder is set to mode 0700, even if it already existed. On Windows the app relies on the user profile's access control list. The app refuses to open a folder on a network filesystem (an SMB, NFS, AFP or WebDAV mount on macOS, a mapped network drive or UNC path on Windows), because SQLite's WAL mode is not safe there.
- **Server.** The app binds `127.0.0.1` on a port the operating system assigns, and hands that already-listening socket to the server, so there is no gap in which another program could take the port. On Windows the socket is exclusive (`SO_EXCLUSIVEADDRUSE`). Only a `Host` header exactly equal to `127.0.0.1:<that port>` is accepted, which refuses DNS-rebinding pages. The `Origin` and `Sec-Fetch-Site` rules, the 2 MB limit and the content security policy above are unchanged.
- **Sign-in.** At each launch the app generates a 256-bit launch code, held only in the process's memory. It is never written to disk, an environment variable or a command line. The window opens `/desktop/start?code=…`. The server accepts the code once, within 30 seconds of the server starting. After that time it refuses the code for good. A wrong code is refused but does not use up the real one. Success sets the ordinary owner session cookie (HttpOnly, SameSite=Strict, no `Domain`, no expiry, so the browser drops it when the window closes) and redirects to `/`, so the code leaves the address. The window runs in pywebview's private mode, which clears its cookies and site data when it starts. On Windows, WebView2 runs InPrivate, and its data folder is set explicitly inside the app's data folder, because the default folder is shared by every pywebview app. On macOS, pywebview ignores that folder: WebKit keeps the window's data in its default store for the application (`~/Library/WebKit/<bundle identifier>`, or `.../python` when run from source) and pywebview clears it at startup. In a check on macOS the session cookie was not found on disk. The session's database row is deleted at shutdown, so a cookie that WebKit did keep would no longer sign anyone in. A row left behind by a crash expires after 30 days. Any other page at that address gets a plain instruction page, not the sign-in form. The paste-a-key `/api/login` and bearer tokens still work as described above, and the app still writes `owner.key` (mode 0600) for command-line use.
- **Logging.** The server's own access log is switched off, because it records query strings and would write the launch code to disk. `desktop.log` records each request's method, path (without the query string) and status, plus start and stop.
- **Window engine.** On Windows the app requires the Microsoft Edge WebView2 Runtime and shows an error if it is missing, instead of letting pywebview fall back to Internet Explorer's engine. The content security policy blocks pywebview's JavaScript bridge, and the app does not use it.
- **One instance.** A lock file in the data folder stops a second copy of the app from opening the same database. Closing the window or quitting the app stops the server, deletes the window's session and checkpoints the WAL into the database file.
- **What this does not protect against.** Any program running as the same operating-system user can read the data folder, including `owner.key` and the database. Any local user or program can connect to the loopback port, but without the launch code or a session it receives only the plain page and `401` responses.

For remote use, provide a reviewed HTTPS reverse proxy, explicit trusted hosts, an exact public origin, restricted network access and protected backups. Set `FOUNDRY_ALLOWED_HOSTS` to comma-separated hostnames (no ports), and `FOUNDRY_PUBLIC_ORIGIN` to the exact HTTPS origin. Configure forwarded headers only from your trusted proxy. This repository does not deploy a cloud service or provision TLS, SSO, MFA, high availability, tenant encryption keys or managed backup storage.

## Credentials and roles

The first initialization creates one owner token and writes it to `owner.key` beside the database with mode 0600. Database directories are created with mode 0700 where new, and the database file is mode 0600. Existing parent-directory permissions are not changed. Tokens have high-entropy random values and are stored only as SHA-256 hashes. This is token authentication, not password hashing.

| Role | Scope | Authority |
|---|---|---|
| Owner | All businesses | Create businesses and keys, prepare work, review, approve and reconcile |
| Reviewer | Assigned businesses | Prepare and make human review decisions |
| Operator | Assigned businesses | Create ordinary records and prepare work; record an approved external submission with reviewed evidence |
| Agent | Assigned businesses | Prepare records, evidence, models and drafts; no human approvals or execution attestations |
| Viewer | Assigned businesses | Read only |

Owners are global even if scope IDs are supplied; the UI does not offer owner-key creation. Only an owner can create/revoke access keys. An owner cannot revoke the key currently authenticating that request. Revocation removes sessions and blocks bearer authentication. Ordinary keys have no automatic expiry in v0.1; revoke them when access ends. The original owner key is powerful and should remain outside AI clients.

Browser sessions are random, hashed, HttpOnly and SameSite=Strict, with an eight-hour expiry and the Secure flag on HTTPS. The desktop app's window session is the exception described above. Login attempts have an in-memory per-client limit. Cross-origin and browser cross-site writes are rejected. A write authenticated only by the session cookie must also show it came from the application itself: an `Origin` header equal to the expected origin (`FOUNDRY_PUBLIC_ORIGIN`, or the request's own origin when that is unset) or `Sec-Fetch-Site: same-origin`. Without either it is refused with HTTP 403. Any write (any method other than GET, HEAD or OPTIONS) that carries more than one `Origin` header, or more than one `Sec-Fetch-Site` header, is refused with HTTP 403 whether it uses the cookie or a bearer token, because a browser never sends two and the values would be ambiguous. Signing in creates the session and has no cookie yet, so it works from the browser and the command line. API callers use bearer tokens, which do not need origin headers. Request bodies have a 2 MB limit. Validation failures omit submitted values. They name only locations defined by the route's declared request model, worked out from the model's structure rather than from the spelling of the input: model field names and list positions are named; an unexpected property is reported as "an unexpected field was sent" at its defined parent; and the location stops at a dictionary field (for example `body.properties`), so client-chosen dictionary keys are never repeated, even when one is spelled like a defined field. A body that is not valid JSON is reported at `body`, without a character position. Avoid logging request bodies or authorization headers at the proxy. Every response the application returns carries a strict content security policy (`script-src 'self'`, `style-src 'self'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` and `Cache-Control: no-store`, and the page loads no third-party resources. This includes refusals made before routing (invalid host, cross-origin or cross-site write, cookie write without origin evidence, duplicate `Origin`, the 2 MB limit), 404 and 422 responses, and an unhandled server error, which returns HTTP 500 with the fixed JSON body `{"detail": "The server could not complete this request."}` and no exception text. The one exception is a reply the HTTP server (for example uvicorn) sends itself before a request reaches the application, such as its response to a malformed HTTP request; it does not carry these headers. If an error occurs after a response has started, the headers were already sent with it and the connection is closed. Because the policy allows no third-party or inline script, FastAPI's Swagger page is switched off; only the schema at `/api/openapi.json` is served.

## Private data

`.foundry/`, `.env*` (except the template), databases, logs, build outputs and test artifacts are ignored by Git. There are no telemetry calls, remote fonts or automatic document fetches. Source URLs are retained as references and are not fetched by the server. The UI escapes business content and displays documents as text; it does not execute imported HTML or load remote resources embedded in evidence.

Private evidence and backups are not encrypted by the application. Use full-disk encryption, OS access controls and encrypted backup storage appropriate to the data. Anyone with filesystem access to the owner token can act as owner; anyone who can edit the database can rewrite authorization and history. The local event chain does not protect against that administrator. Do not expose this deployment to hostile multi-tenant workloads.

The optional AI review shares summaries only after an explicit user request, but summaries can contain confidential content. The MCP adapter can return full business records, including evidence, to its authorized client. These are distinct sharing surfaces; see [AI setup](docs/AI.md). Provider keys are read only from the deployment environment and never inserted into business records.

Exports contain original evidence, internal decisions and AI review requests/responses. Database backups also contain all businesses and credential hashes. Treat both as private. Public examples and screenshots must use explicitly synthetic data; do not publish actual founder, customer, employee, ownership, financial or contracting information without the relevant authorization.

## Recovery and operational limits

`foundry backup` uses SQLite's backup API to produce a consistent snapshot while the source is running. It refuses to overwrite an existing file. `foundry restore` requires an absent destination and checks the source schema and SQLite integrity before copying. Keep the original owner key separately. Test restored backups before treating them as usable.

The JSON export is not a restore format and cannot import authority from another workspace. Invoice and payment records are an operational register. There is no refund/void/correction ledger in this release; an incorrect financial record must be retained, flagged through evidence withdrawal and reconciled in the authoritative accounting system. Add a proper reversal flow before using Foundry as a financial system of record.

## Reporting issues

Do not post secrets, private evidence or real business exports in public issues. Use the repository's GitHub private vulnerability reporting feature if enabled. For a suspected exposure, revoke affected access keys, stop untrusted access, rotate provider credentials where relevant and preserve a private backup for investigation. This policy does not imply a staffed response SLA or an external security audit.
