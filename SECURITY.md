# Security and deployment

## Supported deployment

v0.1 is a local-first alpha for a founder or small team on a trusted machine. Run one application process with its SQLite database on a local disk. The default bind address is `127.0.0.1`; the server rejects unexpected Host headers. Do not put the database on a network filesystem or scale multiple containers against the same SQLite file.

`foundry start` always binds `127.0.0.1` and has no host option; use `foundry serve --host` with the precautions below for any other address. On first run it creates the database and owner key exactly as `init` does. It prints the owner key to its standard output only when that output is a terminal; when the output is piped, redirected or captured by a service manager, it prints instead the command that shows the key, such as `uv run foundry token`, and the folder to run it in. The key is never put in the address it opens in the browser and is not written to the server log (`start` logs warnings and errors only, not requests). Because the key appears on screen, start Foundry where others cannot read your terminal, and do not paste its output into public issues.

### Desktop app

`foundry-desktop` (install the `desktop` extra) shows the same interface in a native window, served by the same application in the same process. Installers, code signing and updates are not built yet.

- **Data location.** The database, `owner.key`, the app's log (`desktop.log`) and the window's site-data folder live in the per-user application data folder: `~/Library/Application Support/Business Foundry` on macOS, `%LOCALAPPDATA%\Business Foundry` on Windows (not the roaming profile), and `~/.local/share/Business Foundry` on Linux, or `$XDG_DATA_HOME/Business Foundry` when that variable is set to an absolute path. On macOS and Linux that folder is set to mode 0700, even if it already existed. On Windows the app relies on the user profile's access control list. The app refuses to open a folder on a network filesystem (an SMB, NFS, AFP or WebDAV mount on macOS, a mapped network drive or UNC path on Windows), because SQLite's WAL mode is not safe there. On Linux the app finds the folder's mount in `/proc/self/mounts` and compares the filesystem type shown there with the app's list of network filesystems, and refuses the folder when the type is on that list. Of that list, the names a Linux table shows are `nfs`, `nfs4`, `cifs`, `smb3`, `fuse.sshfs`, `9p`, `afs`, `ceph`, `fuse.glusterfs` and `lustre`. The list also holds `smbfs`, `smb2`, `afpfs`, `webdav`, `davfs`, `sshfs` and `glusterfs`, and the folder is refused too if the table shows one of those. A network filesystem that the table shows under a type that is not on the list is not recognised, and the folder is opened: an rclone or s3fs mount, for example, which the table shows as `fuse.rclone` or `fuse.s3fs`. If that table cannot be read, the check finds nothing and the folder is opened.
- **Server.** The app binds `127.0.0.1` on a port the operating system assigns, and hands that already-listening socket to the server, so there is no gap in which another program could take the port. On Windows the socket is exclusive (`SO_EXCLUSIVEADDRUSE`). Only a `Host` header exactly equal to `127.0.0.1:<that port>` is accepted, which refuses DNS-rebinding pages. The `Origin` and `Sec-Fetch-Site` rules, the 2 MB limit and the content security policy below are unchanged, except that the expected origin is always the window's own `http://127.0.0.1:<that port>`: `FOUNDRY_PUBLIC_ORIGIN` is ignored, with a note in `desktop.log`, so a value left over from a server deployment cannot block saving.
- **Sign-in.** The window first shows a local "Opening" page. Once it has, the app generates a 256-bit launch code, held only in the process's memory and never written by the app to disk, a log, an environment variable or a command line, and sends the window to `/desktop/start?code=…`. The server accepts that code once, within 180 seconds of it being issued. After that time it refuses the code for good. On macOS and Linux, time the computer spends asleep does not count towards those 180 seconds, or towards the 5-second grace described below, so a code can still be accepted more than 180 seconds after it was issued if the computer slept in between. On Windows, Python's and Microsoft's documentation say that time asleep does count; this has not been tested. The limit is generous because a first start of the web engine on a slow computer can be slow, and it adds little protection: the code's strength is its 256 random bits, its single use and its staying inside the process. If the window presents its code too late, or has not presented it by the time its 180 seconds and a further 5-second grace are up, the app sends the window a new code and the previous one stops working. A code presented in time whose session is still being written when that time is up is waited for until the write ends (it then either signs the window in or counts as refused), and no new code is issued while it is, so a sign-in in progress is never replaced or reported as a failure. At most one code is valid at any moment, at most three are issued per launch, none after the window has signed in or once the app has begun to close, and none is accepted then either. So a launch opens at most one session. If the third also fails, the window says so and asks the user to quit and reopen the app; from that moment no code is accepted, so that message never covers a sign-in that went on to succeed. A wrong code is refused at once, even while the database is busy, and does not use up the real one. Success sets the ordinary owner session cookie (HttpOnly, SameSite=Strict, no `Domain`, no expiry, so the browser drops it when the window closes) and redirects to `/`, so the code leaves the address. The window runs in pywebview's private mode, which clears its cookies and site data when it starts. On Windows, WebView2 runs InPrivate, and its data folder is set explicitly inside the app's data folder, because the default folder is shared by every pywebview app. On macOS, pywebview ignores that folder: WebKit keeps the window's data in its default store for the application (`~/Library/WebKit/<bundle identifier>`, or `.../python` when run from source) and pywebview clears it at startup. In a check on macOS the session cookie was not found on disk. The session's database row is deleted at shutdown, so a cookie that WebKit did keep would no longer sign anyone in. A sign-in that is still writing its session when the app begins to close deletes its own row when the write ends, and sets no cookie. A row left behind by a crash expires after 30 days. Without that session, `/` gets a plain instruction page, not the sign-in form. The paste-a-key `/api/login` and bearer tokens still work as described above, and the app still writes `owner.key` (mode 0600) for command-line use.
- **Logging.** A log record made through the logging module's usual calls (`Logger.debug` to `Logger.critical`, `Logger.log`, `Logger.exception` and the module-level functions such as `logging.warning`) is turned into finished text once, as it is made, before any handler sees it, whatever logger made it and at whatever level its library is set, including pywebview with `PYWEBVIEW_LOG=debug`, whose own console handler writes to stderr. Its message is formatted with its arguments once, and each argument's text is redacted before a format can shorten it (such as `%.20s`), so a shortened argument cannot print part of a code. A logged exception is formatted once too. Handlers then receive that finished text, not the arguments or the exception: on every such record `msg` is the finished text, an exact `str` even when the caller passed another object, `args` and `exc_info` are `None`, and a logged exception's text is in `exc_text`, in the standard form and redacted. So a handler that reads `msg`, `args` or `exc_info` itself gets those values, not what the caller passed, and a formatter's own `formatException` is not used: the standard exception text is printed instead. Nothing the app installs reads those fields itself or has its own `formatException`. In the message, the exception text and the stack, a whole launch code or the window's session token is replaced by `[redacted]`, and so is everything after `/desktop/start?` up to the next whitespace, whatever it holds. A start address is recognised by the text `/desktop/start?`. Written another way, for example with the `?` or the path percent-encoded, it is not recognised as a start address, though a whole code in it is still replaced. A code or token is recognised as its exact text. A piece of one, or one written another way such as percent-encoded, is not recognised outside a start address. For example, a caller that cuts a code into pieces and logs each piece leaves nothing to recognise. The parts of a record that are checked are its message with its arguments, its exception text and its stack; its other fields, such as the logger's name or the thread's name, are not, and `desktop.log`'s formatter redacts its whole finished line. When a record's arguments fit its message, each argument is converted to text once for each place the format names it, while the record is finished, and not again for each handler; without the redaction, each handler would convert it again. In every case, an argument whose text changes from one conversion to the next prints the same text at every handler: the text of the conversions made while the record was finished. A record prints the same message as without the redaction when its arguments fit its message, its message and each argument can be turned into text and give the same text each time they are converted, it holds no secret and no start address, and it is not one of the three forms named below. Those are the differences known; there may be others. A record whose arguments do not fit its message, for example too few for its fields, is still written: the message as it stands, a space, then the `repr` of the arguments, redacted, such as `two %s %s ('one',)`. The logging module alone would print a `--- Logging error ---` report to stderr and write no record. An argument that the format had already converted before it failed is converted once more for that `repr`, and the `repr` is what is printed. Three forms that fit for Python alone are written that way too: `%c` given a one-character instance of a `str` subclass, and a `*` width or precision (`%*d`, `%.*s`) given an instance of an `int` subclass, such as an `IntEnum` member. The cause is that an argument whose type is exactly `str`, `int`, `float`, `bool` or `None` is given to the format as it is (a `str` after redaction), and any other argument gets a stand-in. `%c` accepts a stand-in only when the real value is a number, and a `*` accepts only a real `int`. No secret is at risk in these forms; only the printed text differs. A record that cannot be finished, for example because an argument cannot be turned into text, is withheld and replaced by a short note. A record built another way (`logging.makeLogRecord`, or `logging.LogRecord` called directly) is not finished as it is made. The first of the handlers that existed when logging was set up and when the window library loaded to receive it finishes it by the same rule, and `desktop.log`'s formatter checks it too, so it does not reach `desktop.log` unchecked. A handler that some library adds later, and that receives it before those handlers do, would print it unchecked. Nothing the app installs builds records that way. A field added to a record with `extra=` is added after the record is made, and it is not checked. A handler whose format prints that field would print a code or token passed that way. `desktop.log`'s format prints no such field, and nothing the app installs passes a code or token that way. Further layers stay in place: the server's own access log is switched off, because it records query strings, and the HTTP client library's request log is limited to warnings. `desktop.log` records each request's method, path (without the query string) and status, each launch code being issued, refused or used (never the code itself), plus start and stop. Text written to the console without the logging module, or by the web engine's native code, is not filtered. The web engine does not log addresses unless its own logging is turned on, for example through Qt's `QTWEBENGINE_CHROMIUM_FLAGS`.
- **Window engine.** On Windows the app requires the Microsoft Edge WebView2 Runtime and shows an error if it is missing, instead of letting pywebview fall back to Internet Explorer's engine. The content security policy blocks pywebview's JavaScript bridge, and the app does not use it.
- **One instance and shutdown.** A lock file in the data folder stops a second copy of the app from opening the same database. Closing the window or quitting the app stops the server, deletes the window's session and checkpoints the WAL into the database file. Ctrl+C, `SIGTERM` and `SIGHUP` take the same path on macOS and Linux, whichever thread the operating system delivers them to, including threads started by other code before the app's own entry point, and from the moment the app's handler for a signal is installed none is lost. The app ends its own process no later than 30 seconds after it receives such a signal, whatever the window, the server or the database are doing. Time the computer spends asleep does not count towards those 30 seconds. If the app is paused, or the computer is too busy to run it, when the 30 seconds are up, it ends as soon as it runs again. The window first has 10 seconds to close the normal way. If the app has not finished stopping by then, it runs the cleanup itself and exits when that is done; whatever is still unfinished at 30 seconds is abandoned, with the same consequences as a crash. Nothing can clean up after `SIGKILL`, a crash or power loss. Committed records are still safe, because SQLite recovers its WAL on the next start, and the leftover session row expires as described above. On Windows, which is not yet tested, the operating system does not send these signals to a windowed app. Ending it from Task Manager first asks the window to close, which should run the normal shutdown, and a forced kill gets no cleanup.
- **What this does not protect against.** Any program running as the same operating-system user can read the data folder, including `owner.key` and the database. Any local user or program can connect to the loopback port. Without the launch code or a session it can get only: the plain instruction page at `/`, and at `/desktop/start` without a valid code (both HTTP 403); the interface's own scripts, styles and logo under `/static/`, which hold no records; `/api/health`, which gives the status and version; the API schema at `/api/openapi.json`; and `/api/login`, which signs in only with a valid access key. Every other route answers `401`. A test walks every route the desktop app registers and fails on one that is not in this list and does not answer `401`.

For remote use, provide a reviewed HTTPS reverse proxy, explicit trusted hosts, an exact public origin, restricted network access and protected backups. Set `FOUNDRY_ALLOWED_HOSTS` to comma-separated hostnames (no ports), and `FOUNDRY_PUBLIC_ORIGIN` to the exact HTTPS origin. Configure forwarded headers only from your trusted proxy. This repository does not deploy a cloud service or provision TLS, SSO, MFA, high availability, tenant encryption keys or managed backup storage.

## Credentials and roles

The first initialization creates one owner token and writes it to `owner.key` beside the database with mode 0600. Database directories are created with mode 0700 where new, and the database file is mode 0600. Existing parent-directory permissions are not changed. Tokens have high-entropy random values and are stored only as SHA-256 hashes. This is token authentication, not password hashing.

| Role | Scope | Authority |
|---|---|---|
| Owner | All businesses | Create businesses and keys, prepare work, review, approve, reconcile and change the planning jurisdiction |
| Reviewer | Assigned businesses | Prepare and make human review decisions, including a planning-jurisdiction change |
| Operator | Assigned businesses | Create ordinary records and prepare work; record an approved external submission with reviewed evidence |
| Agent | Assigned businesses | Prepare records, evidence, models and drafts; no human approvals, execution attestations or jurisdiction changes |
| Viewer | Assigned businesses | Read only |

Owners are global even if scope IDs are supplied; the UI does not offer owner-key creation. Only an owner can create/revoke access keys. An owner cannot revoke the key currently authenticating that request. Revocation removes sessions and blocks bearer authentication. Ordinary keys have no automatic expiry in v0.1; revoke them when access ends. The original owner key is powerful and should remain outside AI clients.

Browser sessions are random, hashed, HttpOnly and SameSite=Strict, with an eight-hour expiry and the Secure flag on HTTPS. The desktop app's window session is the exception described above. Login attempts have an in-memory per-client limit. Cross-origin and browser cross-site writes are rejected. A write authenticated only by the session cookie must also show it came from the application itself: an `Origin` header equal to the expected origin (`FOUNDRY_PUBLIC_ORIGIN`, or the request's own origin when that is unset) or `Sec-Fetch-Site: same-origin`. Without either it is refused with HTTP 403. Any write (any method other than GET, HEAD or OPTIONS) that carries more than one `Origin` header, or more than one `Sec-Fetch-Site` header, is refused with HTTP 403 whether it uses the cookie or a bearer token, because a browser never sends two and the values would be ambiguous. Signing in creates the session and has no cookie yet, so it works from the browser and the command line. API callers use bearer tokens, which do not need origin headers. Request bodies have a 2 MB limit. Validation failures omit submitted values. They name only locations defined by the route's declared request model, worked out from the model's structure rather than from the spelling of the input: model field names and list positions are named; an unexpected property is reported as "an unexpected field was sent" at its defined parent; and the location stops at a dictionary field (for example `body.properties`), so client-chosen dictionary keys are never repeated, even when one is spelled like a defined field. A body that is not valid JSON is reported at `body`, without a character position. Avoid logging request bodies or authorization headers at the proxy. Every response the application returns carries a strict content security policy (`script-src 'self'`, `style-src 'self'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` and `Cache-Control: no-store`, and the page loads no third-party resources. This includes refusals made before routing (invalid host, cross-origin or cross-site write, cookie write without origin evidence, duplicate `Origin`, the 2 MB limit), 404 and 422 responses, and an unhandled server error, which returns HTTP 500 with the fixed JSON body `{"detail": "The server could not complete this request."}` and no exception text. The one exception is a reply the HTTP server (for example uvicorn) sends itself before a request reaches the application, such as its response to a malformed HTTP request; it does not carry these headers. If an error occurs after a response has started, the headers were already sent with it and the connection is closed. Because the policy allows no third-party or inline script, FastAPI's Swagger and ReDoc pages are switched off; only the schema at `/api/openapi.json` is served.

## Private data

`.foundry/`, `.env*` (except the template), databases, logs, build outputs and test artifacts are ignored by Git. There are no telemetry calls, remote fonts or automatic document fetches. Source URLs are retained as references and are not fetched by the server. The UI escapes business content and displays documents as text; it does not execute imported HTML or load remote resources embedded in evidence. It shows a stored source URL as a link only if it is an `http:` or `https:` address; anything else is shown as plain text, as a second line of defence behind the server's validation. Signing out, or a request refused because the session has ended, clears the previous person's records from the page and from the interface's memory. The tabs of the page in one browser share one session cookie, so a sign-in, a sign-out or an ended session in one tab changes who is signed in for all of them. The tab where it happens tells the other open tabs of the same address through the browser's `BroadcastChannel`: when its sign-in is accepted, when its sign-out is answered, and when the server refuses one of its requests because the session has ended. The message is one fixed word and carries no key, token, name, record or business id. A tab that receives it clears the previous person's records, waiting answers, queued dialogs and any key it shows, as signing out does in that tab, then asks the server who is signed in and shows that person's workspace or the sign-in page, with one sentence saying that the sign-in changed in another tab and naming any form it closed. If someone signs in or out in that tab before the answer arrives, the tab follows that and says nothing about the other tab, and after a sign-in only the answer to that sign-in is acted on. A key typed into the sign-in field of such a tab and never sent is cleared before a workspace is shown there. Receiving the message can only make a tab forget and ask again; a message of any other shape is ignored, and a tab that is told sends nothing in turn. Any answer that arrives after a session has ended in a tab, a newly created access key included, is discarded: it opens no dialog, shows no message and is kept in no element or variable of the page, even after a new sign-in. A new access key is shown once, and its text leaves the page when its dialog is closed. Just before it is shown, the page asks the server who is signed in. It shows the key only if the answer names the same principal id that asked for it and nothing has ended that tab's session meanwhile. For anyone else the key is dropped and the tab starts again; if the server cannot be reached, the key is not shown, and a notice says that a key with that name was created and cannot be shown, and to revoke it and create a new one. This check works without the message, for example in a browser without `BroadcastChannel`. Its limit: the server names a person, not a session, so if the same person signs out and in again in another tab and the message is lost, the key is shown to that same person. Once the key is on screen, a later change of sign-in in another tab closes its dialog only through the message. A sign-out still waiting for its answer is cancelled when its tab learns that the session ended or changed, by a refused request or by the message, because its answer deletes the cookie the tabs share. An answer that reaches the browser before then still deletes that cookie, even if another tab has signed in since, and the person is asked to sign in again; preventing that needs a change on the server.

Private evidence and backups are not encrypted by the application. Use full-disk encryption, OS access controls and encrypted backup storage appropriate to the data. Anyone with filesystem access to the owner token can act as owner; anyone who can edit the database can rewrite authorization and history. `foundry verify` detects a changed event unless every hash from it onward is rewritten and, while the chain is intact, a changed value in current records, revision snapshots or stored content hashes. Anyone who can edit the database can also append correctly chained events without changing any earlier hash: an appended event that records a changed record as a new version, with a matching revision unless it is the business profile, which has none, or that matches a changed AI review, passes verification. [Architecture](docs/ARCHITECTURE.md#integrity-and-recovery) lists exactly what is and is not compared. The local event chain does not protect against that administrator: someone who rewrites the records, revisions and every chained hash consistently, or appends events that match them, will pass verification. Do not expose this deployment to hostile multi-tenant workloads.

The optional AI review shares summaries only after an explicit user request, but summaries can contain confidential content. The MCP adapter can return full business records, including evidence, to its authorized client. These are distinct sharing surfaces; see [AI setup](docs/AI.md). Provider keys are read only from the deployment environment and never inserted into business records.

Exports contain original evidence, internal decisions and AI review requests/responses. Database backups also contain all businesses and credential hashes. Treat both as private. Public examples and screenshots must use explicitly synthetic data; do not publish actual founder, customer, employee, ownership, financial or contracting information without the relevant authorization.

## Recovery and operational limits

`foundry backup` uses SQLite's backup API to produce a consistent snapshot while the source is running. It refuses to overwrite an existing file. It refuses a source that does not exist or is not a Foundry database, and in that case Foundry creates no database, no backup file and no folder. Whether the backup is refused or succeeds, the source's database file is not changed, but if the source is an SQLite database in WAL mode, SQLite may add its own two working files beside it as it opens it to read, named like the database with `-wal` and `-shm` on the end; Foundry leaves them there, because a running server may be using them. `foundry restore` requires an absent destination and checks the source schema and SQLite integrity before copying. Keep the original owner key separately. Test restored backups before treating them as usable.

The JSON export is not a restore format and cannot import authority from another workspace. Invoice and payment records are an operational register. There is no refund/void/correction ledger in this release; an incorrect financial record must be retained, flagged through evidence withdrawal and reconciled in the authoritative accounting system. Add a proper reversal flow before using Foundry as a financial system of record.

## Reporting issues

Do not post secrets, private evidence or real business exports in public issues. Use the repository's GitHub private vulnerability reporting feature if enabled. For a suspected exposure, revoke affected access keys, stop untrusted access, rotate provider credentials where relevant and preserve a private backup for investigation. This policy does not imply a staffed response SLA or an external security audit.
