# Security and deployment

## Supported deployment

v0.1 is a local-first alpha for a founder or small team on a trusted machine. Run one application process with its SQLite database on a local disk. The default bind address is `127.0.0.1`; the server rejects unexpected Host headers. Do not put the database on a network filesystem or scale multiple containers against the same SQLite file.

For remote use, provide a reviewed HTTPS reverse proxy, explicit trusted hosts, an exact public origin, restricted network access and protected backups. Set `FOUNDRY_ALLOWED_HOSTS` to comma-separated hostnames (no ports), and `FOUNDRY_PUBLIC_ORIGIN` to the exact HTTPS origin. Configure forwarded headers only from your trusted proxy. This repository does not deploy a cloud service or provision TLS, SSO, MFA, high availability, tenant encryption keys or managed backup storage.

## Credentials and roles

The first initialization creates one owner token and writes it to `owner.key` beside the database with mode 0600. Database directories are created with mode 0700 where new, and the database file is mode 0600. Existing parent-directory permissions are not changed. Tokens have high-entropy random values and are stored only as SHA-256 hashes. This is token authentication, not password hashing.

| Role | Scope | Authority |
|---|---|---|
| Owner | All businesses | Create businesses and keys, prepare work, review, approve, reconcile and change the planning jurisdiction |
| Reviewer | Assigned businesses | Prepare and make human review decisions, including a planning-jurisdiction change |
| Operator | Assigned businesses | Create ordinary records and prepare work; record an approved external submission with reviewed evidence |
| Agent | Assigned businesses | Prepare records, evidence, models and drafts; no human approvals, execution attestations or jurisdiction changes |
| Viewer | Assigned businesses | Read only |

Owners are global even if scope IDs are supplied; the UI does not offer owner-key creation. Only an owner can create/revoke access keys. An owner cannot revoke the key currently authenticating that request. Revocation removes sessions and blocks bearer authentication. Ordinary keys have no automatic expiry in v0.1; revoke them when access ends. The original owner key is powerful and should remain outside AI clients.

Browser sessions are random, hashed, HttpOnly and SameSite=Strict, with an eight-hour expiry and the Secure flag on HTTPS. Login attempts have an in-memory per-client limit. Cross-origin and browser cross-site writes are rejected. A write authenticated only by the session cookie must also show it came from the application itself: an `Origin` header equal to the expected origin (`FOUNDRY_PUBLIC_ORIGIN`, or the request's own origin when that is unset) or `Sec-Fetch-Site: same-origin`. Without either it is refused with HTTP 403. Any write (any method other than GET, HEAD or OPTIONS) that carries more than one `Origin` header, or more than one `Sec-Fetch-Site` header, is refused with HTTP 403 whether it uses the cookie or a bearer token, because a browser never sends two and the values would be ambiguous. Signing in creates the session and has no cookie yet, so it works from the browser and the command line. API callers use bearer tokens, which do not need origin headers. Request bodies have a 2 MB limit. Validation failures omit submitted values. They name only locations defined by the route's declared request model, worked out from the model's structure rather than from the spelling of the input: model field names and list positions are named; an unexpected property is reported as "an unexpected field was sent" at its defined parent; and the location stops at a dictionary field (for example `body.properties`), so client-chosen dictionary keys are never repeated, even when one is spelled like a defined field. A body that is not valid JSON is reported at `body`, without a character position. Avoid logging request bodies or authorization headers at the proxy. Every response the application returns carries a strict content security policy (`script-src 'self'`, `style-src 'self'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` and `Cache-Control: no-store`, and the page loads no third-party resources. This includes refusals made before routing (invalid host, cross-origin or cross-site write, cookie write without origin evidence, duplicate `Origin`, the 2 MB limit), 404 and 422 responses, and an unhandled server error, which returns HTTP 500 with the fixed JSON body `{"detail": "The server could not complete this request."}` and no exception text. The one exception is a reply the HTTP server (for example uvicorn) sends itself before a request reaches the application, such as its response to a malformed HTTP request; it does not carry these headers. If an error occurs after a response has started, the headers were already sent with it and the connection is closed. Because the policy allows no third-party or inline script, FastAPI's Swagger page is switched off; only the schema at `/api/openapi.json` is served.

## Private data

`.foundry/`, `.env*` (except the template), databases, logs, build outputs and test artifacts are ignored by Git. There are no telemetry calls, remote fonts or automatic document fetches. Source URLs are retained as references and are not fetched by the server. The UI escapes business content and displays documents as text; it does not execute imported HTML or load remote resources embedded in evidence. It shows a stored source URL as a link only if it is an `http:` or `https:` address; anything else is shown as plain text, as a second line of defence behind the server's validation. Signing out, or a request refused because the session has ended, clears the previous person's records from the page and from the interface's memory. The tabs of the page in one browser share one session cookie, so a sign-in, a sign-out or an ended session in one tab changes who is signed in for all of them. The tab where it happens tells the other open tabs of the same address through the browser's `BroadcastChannel`: when its sign-in is accepted, when its sign-out is answered, and when the server refuses one of its requests because the session has ended. The message is one fixed word and carries no key, token, name, record or business id. A tab that receives it clears the previous person's records, waiting answers, queued dialogs and any key it shows, as signing out does in that tab, then asks the server who is signed in and shows that person's workspace or the sign-in page, with one sentence saying that the sign-in changed in another tab and naming any form it closed. A key typed into the sign-in field of such a tab and never sent is cleared before a workspace is shown there. Receiving the message can only make a tab forget and ask again; a message of any other shape is ignored, and a tab that is told sends nothing in turn. Any answer that arrives after a session has ended in a tab, a newly created access key included, is discarded: it opens no dialog, shows no message and is kept in no element or variable of the page, even after a new sign-in. A new access key is shown once, and its text leaves the page when its dialog is closed. Just before it is shown, the page asks the server who is signed in. It shows the key only if the answer names the same principal id that asked for it and nothing has ended that tab's session meanwhile. For anyone else the key is dropped and the tab starts again; if the server cannot be reached, the key is not shown, and a notice says that a key with that name was created and cannot be shown, and to revoke it and create a new one. This check works without the message, for example in a browser without `BroadcastChannel`. Its limit: the server names a person, not a session, so if the same person signs out and in again in another tab and the message is lost, the key is shown to that same person. Once the key is on screen, a later change of sign-in in another tab closes its dialog only through the message. A sign-out still waiting for its answer is cancelled when its tab learns that the session ended or changed, by a refused request or by the message, because its answer deletes the cookie the tabs share. An answer that reaches the browser before then still deletes that cookie, even if another tab has signed in since, and the person is asked to sign in again; preventing that needs a change on the server.

Private evidence and backups are not encrypted by the application. Use full-disk encryption, OS access controls and encrypted backup storage appropriate to the data. Anyone with filesystem access to the owner token can act as owner; anyone who can edit the database can rewrite authorization and history. `foundry verify` detects a changed event unless every hash from it onward is rewritten and, while the chain is intact, a changed value in current records, revision snapshots or stored content hashes. Anyone who can edit the database can also append correctly chained events without changing any earlier hash: an appended event that records a changed record as a new version, with a matching revision unless it is the business profile, which has none, or that matches a changed AI review, passes verification. [Architecture](docs/ARCHITECTURE.md#integrity-and-recovery) lists exactly what is and is not compared. The local event chain does not protect against that administrator: someone who rewrites the records, revisions and every chained hash consistently, or appends events that match them, will pass verification. Do not expose this deployment to hostile multi-tenant workloads.

The optional AI review shares summaries only after an explicit user request, but summaries can contain confidential content. The MCP adapter can return full business records, including evidence, to its authorized client. These are distinct sharing surfaces; see [AI setup](docs/AI.md). Provider keys are read only from the deployment environment and never inserted into business records.

Exports contain original evidence, internal decisions and AI review requests/responses. Database backups also contain all businesses and credential hashes. Treat both as private. Public examples and screenshots must use explicitly synthetic data; do not publish actual founder, customer, employee, ownership, financial or contracting information without the relevant authorization.

## Recovery and operational limits

`foundry backup` uses SQLite's backup API to produce a consistent snapshot while the source is running. It refuses to overwrite an existing file. `foundry restore` requires an absent destination and checks the source schema and SQLite integrity before copying. Keep the original owner key separately. Test restored backups before treating them as usable.

The JSON export is not a restore format and cannot import authority from another workspace. Invoice and payment records are an operational register. There is no refund/void/correction ledger in this release; an incorrect financial record must be retained, flagged through evidence withdrawal and reconciled in the authoritative accounting system. Add a proper reversal flow before using Foundry as a financial system of record.

## Reporting issues

Do not post secrets, private evidence or real business exports in public issues. Use the repository's GitHub private vulnerability reporting feature if enabled. For a suspected exposure, revoke affected access keys, stop untrusted access, rotate provider credentials where relevant and preserve a private backup for investigation. This policy does not imply a staffed response SLA or an external security audit.
